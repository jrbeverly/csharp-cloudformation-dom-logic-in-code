# Technical

## Language and Platform

The implementation should be built in C#.

The design should represent the CloudFormation domain object model directly in C#.

The system is conceptually similar to Python Troposphere, but implemented using C# language features and idioms.

## Initial CloudFormation Resource Coverage

Initial resource support should include:

- IAM roles
- SSM parameters
- S3 resources
- Other lightweight or effectively free infrastructure resources

Full CloudFormation resource coverage is explicitly out of scope for the initial effort.

## Prohibited Technical Patterns

The domain model must not rely on:

- `dynamic`
- Generic `object` containers
- Universal catch-all interfaces
- Weakly typed property bags

These patterns should not be used as escape hatches for modelling CloudFormation values.

## Strongly Typed Value Objects

Major CloudFormation resource properties should use explicit value objects rather than raw strings or generic containers.

The system should include value objects for concepts such as:

- IAM role names
- SSM parameter names
- S3 bucket names
- CloudFormation expressions
- Literal values
- Deferred values
- Calculated/composed values

## Intrinsic Function Support

The model must support CloudFormation intrinsic/helper functions, especially:

- `Ref`
- `Sub`
- Other CloudFormation intrinsic functions as needed

Intrinsic functions must compose with strongly typed value objects without collapsing into weak typing.

## Deferred Evaluation

The value model must distinguish between:

- Literal physical values known immediately
- CloudFormation expressions
- Values generated by `Ref`
- Values generated by `Sub`
- Calculated compositions of other values
- Values only known at deployment time

Deferred values must still preserve their eventual constrained type where possible.

For example, an expression that resolves to an SSM parameter name should not become an untyped generic expression if the target domain type is known.

## Naming and Validation

Naming constraints should be encoded directly into relevant value objects where practical.

Examples:

- SSM parameter names should encode relevant path, regex, and naming requirements.
- S3 bucket names should encode S3-specific naming rules.
- IAM role names should encode IAM-specific limitations and conventions.

Validation should be domain-specific rather than centralized in a weak generic property system.

## Serialization

The model must serialize into valid CloudFormation templates.

Serialization must preserve:

- Literal values
- Intrinsic functions
- Deferred expressions
- Resource definitions
- Type-specific CloudFormation semantics

The generated templates should be deployable in AWS for validation.

## Developer Experience

The API should remain ergonomic and composable.

The type system should guide correct usage without becoming excessively granular or difficult to use.

Avoid creating unnecessary hierarchies for simple concepts unless there are meaningful constraints or semantics to encode.
